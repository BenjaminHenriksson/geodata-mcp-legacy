What is an MCP,
and what is this one?

A practical read for anyone who has heard the word "MCP" and wants to understand what this specific thing does, what it doesn't, and where its rough edges are. Aimed at readers coming from a planning, municipal, or GIS background. No prior ML background assumed.

01 / Basics

What an MCP server is

MCP stands for Model Context Protocol. It is an open specification — vendor-neutral and supported across the industry — that lets a chat-based AI call structured tools and read structured data while the user is talking to it. Think of it as a standard plug: any model that understands MCP can connect to any server that offers one.

MCP-capable clients today include ChatGPT (custom connectors), Claude (claude.ai, Claude Desktop, Claude Code), Google Gemini, Qwen Chat, and a growing list of open-source clients — the protocol is genuinely vendor-neutral, and this server doesn't know or care which one is on the other end. The connect-flow examples on the landing page show claude.ai first because that is what was tested first, but the same endpoint URL drops cleanly into any other MCP-capable app.

The arrangement looks like this:

You ↔ Your AI app (MCP client) ↔ MCP server ↔ Tools, data ↕ The model (any LLM — ChatGPT, Claude, Gemini, …)

A small but load-bearing distinction: the model (the LLM itself — whichever one you use, ChatGPT or Claude or Gemini or Qwen or another) is not the same thing as the app you type into. The model runs on its provider's servers. The app is the software on your computer or in your browser: the chatgpt.com or claude.ai website, a desktop app, or a terminal program. In the Model Context Protocol's vocabulary, that app is called the MCP client.

The client sits between you and the model. When you type a question, the client sends it to the model and waits for a reply. When the model decides to call a tool, the client does the actual network call to the MCP server, reads the result, and hands it back to the model. When the model is done, the client shows you the answer. The model decides what to call; the client does the calling. From the MCP server's perspective, it doesn't matter which app or which model is on the other end; the protocol is the same.

So: you ask the AI a question, the model decides what to do, the client makes the tool calls, the model reads the results, and eventually you see an answer. The server never sees your natural-language prompt; it only sees the structured tool calls. You usually don't see the individual tool calls either (unless the client chooses to show them); you see the answer.

Each MCP server offers a fixed, discoverable catalogue of tools. Every tool has a name, a description, argument types, and a machine-readable annotation of whether it is safe to call automatically (read-only) or needs the user's permission (destructive). The AI's client library reads this catalogue at connection time and uses it to decide what to call.

The key idea: the AI does not have magical access to anything you have not explicitly given it a tool for. An MCP server is a bounded surface. If a tool isn't in the catalogue, the action isn't available.

02 / This server

How this MCP works

Geodata MCP is an MCP server that exposes Stockholm's open municipal geodata to an AI chat. The catalogue includes SCB DeSO demographics, the SBK Stadskarta, and OSM addresses, pre-projected to EPSG:3011 and pre-joined to canonical keys. The server offers roughly forty tools: load a dataset, filter, intersect, classify, export, render a map image, and so on.

A typical session looks like this:

  1. You open your AI app (ChatGPT, claude.ai, Gemini, Claude Desktop or Code, or any other MCP-capable client) and connect to this server once, entering an invite code. That setup step is one-off.
  2. You ask a question in plain Swedish or English. Something like: Vilka fem DeSO:n i Stockholm har högst medianinkomst, och hur ser bebyggelsen runt omkring ut?
  3. The model decides which tools to call. It might load the SCB income layer, join it with the SBK building layer, run a spatial buffer, classify the result, and call show() to mark the layers visible in a viewer.
  4. You get back an answer and a private viewer URL that shows the map. The viewer auto-refreshes as the model does more work.
  5. If you want a shareable image of the map, the model calls render_map() and hands you a PNG URL valid for twenty-four hours. You embed it in whatever document you are writing.

Everything runs in a session, a private workspace keyed to your connection. Your session has its own database, its own layers, its own visible styles. Nobody else can see it. If you close the app and come back tomorrow, the session is still there; analyses resume where they left off.

Why it is stateful, and why that matters

Most web APIs are stateless: each request stands alone, the server forgets it the moment it is done, and the client has to include everything the server needs to do its job. That works well for simple request-response shapes. It works badly for the kind of iterative, composable work an LLM does when it analyses data.

This MCP server is stateful within a session. When the model calls load("scb_income"), the resulting layer stays in your session. The next call, filter(...), operates on that loaded layer by name, not on a re-fetched copy. The call after that, annotate(...), writes columns into the same table. Twenty operations can compose over a shared workspace without re-downloading, re-projecting, or re-joining anything. The viewer looks at the same state.

This is one of the problems the Model Context Protocol is explicitly trying to solve. Earlier "function-calling" patterns for LLMs were stateless: every tool call was a self-contained RPC, and the LLM had to re-assemble context each time. That burns tokens (the LLM re-reads the same data repeatedly), burns time (network round-trips add up), and makes certain workflows effectively impossible (a five-step analysis would blow past context limits). MCP's session model gives the server a place to keep durable state that the LLM can reference by name, instead of by content.

Concretely, this session stores: the DuckDB database, the set of layers you have loaded, their column schemas and provenance, styles you have applied in the viewer, your operation history, any checkpoints you have created, and pagination cursors for in-progress iteration. All of that is persistent on disk on this server, so it survives reconnects and even service restarts. A session abandoned for two weeks gets cleaned up; a session you come back to tomorrow is exactly where you left it.

Everything the AI sees is authoritative

The tools the AI calls are authoritative. Spatial joins use real DuckDB spatial SQL over the actual source data, with the correct coordinate reference system. There is no "AI pretending to know geography." Every number in the answer was computed by a deterministic query against a named dataset, and every dataset carries its licence and citation all the way through the analysis.

03 / Pitfalls

Common misunderstandings

These are the things people trip on repeatedly. Most of them are corrections to intuitions imported from other tools (ArcGIS, QGIS, Excel, general-purpose chatbots, web search).

Pitfall 01

It is not a search engine

The AI does not have random-access memory of all 66 datasets. Every tool call retrieves exactly what it asks for. If you ask a vague question, the model will narrow it down by calling search_data or describe_dataset first to find the right table. It is not searching a pre-built index of everything.

This means a question like "what does the data say about Södermalm" will not get a one-shot answer. The model will iteratively pull relevant layers and join them. That takes a handful of seconds but is more accurate than a keyword search would be.

Pitfall 02

Memory lives on the server, not in the model

The model has no persistent memory of your previous conversations. Each new chat starts fresh on the model side. What continuity you get across days comes from the session state stored on this server (layers, styles, operation log), which the model rereads when you reconnect. The AI itself does not carry anything forward.

Separately, on training: most consumer chat plans — across providers (OpenAI, Anthropic, Google, Alibaba, …) — may use conversations to improve future models unless you are on a plan that opts out (most enterprise and API tiers do). Whether that matters for your work depends on what you discuss and which provider you are using. The data this MCP exposes is public municipal data, so nothing confidential leaves your organisation through the chat, but if you paste internal documents into the prompt, that is a different question. Check the specifics of your AI plan if you are not sure.

Nothing the MCP server stores (session state, exported files) leaves this server or feeds back into any model's training.

Pitfall 03

LLM-authored columns are not the same as loaded data

You can ask the model to classify every feature in a layer: tag each stadsdel with a dominant architectural era, for example. That works, and the values are written into a column as if they came from the source. But they did not. The model invented them based on its training data plus whatever context you supplied.

The server tracks this. Every in-session column carries provenance: LLM-authored via annotate by model gpt-5 on 2026-04-19, or … by claude-opus-4-7, or … by gemini-2.5-pro, or derived via add_field with this SQL expression. The viewer and sources() tool surface the distinction regardless of which model wrote the column — the audit trail is provider-agnostic.

Check before you trust. If a column's values came from the LLM, treat them as candidate classifications to verify, not authoritative data. Spot-check a few and iterate.
Pitfall 04

It is not a replacement for ArcGIS or QGIS

This MCP is optimised for ad-hoc conversational queries that end in a rendered answer or a downloadable file. It is not for production cartography, not for complex map composition, not for manual feature editing, and not for raster or terrain analysis (no DEM loaded today).

For those workflows, export the relevant layer as a GeoPackage and open it in ArcGIS or QGIS. The MCP is where you decide what to export; ArcGIS and QGIS are where you polish it for print.

Pitfall 05

The model can still hallucinate around the data

The numbers the model reads from tool calls are authoritative. The prose the model writes around those numbers is subject to the usual AI failure modes: misreading a column, confusing similar place names, inventing a plausible-sounding explanation for a pattern. This is true of every frontier model. The data is trustworthy; the storytelling on top of it needs the same scepticism you would apply to any AI-generated prose.

Rule of thumb: if the model makes a claim, check it against the underlying layer. inspect and stats give you the raw rows and aggregates. If the prose and the rows disagree, trust the rows. The viewer's audit panel also shows the exact SQL the model ran, so you can verify each step instead of just the conclusion.

Pitfall 06

Sessions are private by default, not secret

Your session and its viewer URL are private to you until you share them. There is no shared workspace across users. If you want someone else to see your map, you send them the viewer URL. They can look, but they cannot tool-call against it; their own questions start a fresh session.

Conversely, the viewer URL has no password. Anyone you send it to can see the map. Only send it to people who should see the analysis.

Pitfall 07

Ad-hoc exploration, not a pipeline

This is the right tool for let me look at this quickly and what would that tell me. It is the wrong tool for a nightly-refreshed production job. The session model, the LLM-in-the-loop, and the 24-hour export TTL all assume exploratory work.

If an analysis becomes a recurring need, port it out: the SQL the model writes is standard DuckDB, and the datasets are all publicly downloadable. A production pipeline is a different problem.

Pitfall 08

The AI is a collaborator, not a spec

The model responds to ambiguity by making judgement calls. If your question is underspecified, it will pick a reasonable interpretation and proceed. That interpretation might not be yours.

The cure is to read what the model did. The tool call log is usually visible in the client, and the viewer's audit panel shows every SQL statement plus the rationale the model wrote for each call. Ask follow-ups. Treat it as a capable helper with good instincts, not a mind-reader.

04 / Try it

How to start

Access is invite-only. If you do not have a code, ask; the list of people with codes is currently small. With a code, the set-up is the same as adding any other custom MCP connector to your AI app — ChatGPT, claude.ai, Gemini, or another MCP-capable client: a one-time paste of the endpoint URL, a confirmation screen, and the invite code. Each app's connector dialog looks slightly different, but the protocol underneath is identical.

The full connect flow and tool catalogue are on the landing page and in the docs. The docs cover design rationale, architecture, the data model, and the current roadmap.

Ask a question that matters for your work. The best way to see what this is good for is to use it on something concrete.

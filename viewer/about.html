Primer · For newcomers

What is an MCP,
and what is this one?

A practical read for anyone who has heard the word "MCP" and wants to understand what this specific thing does, what it doesn't, and where its rough edges are. Aimed at readers coming from a planning, municipal, or GIS background. No prior ML background assumed.

01 / Basics

What an MCP server is

MCP stands for Model Context Protocol. It is an open specification for letting a chat-based AI (Claude, ChatGPT, and others) call structured tools and read structured data while the user is talking to it. Think of it as a standard plug: the AI learned how the plug works once, and now it can connect to any server that offers one.

The arrangement looks like this:

You ↔ Your Claude app (MCP client) ↔ MCP server ↔ Tools, data ↕ Claude (AI)

A small but load-bearing distinction: Claude (the AI, the LLM, the model) is not the same thing as the Claude app you type into. Claude itself is a large model running on Anthropic's servers. The app is the software on your computer or in your browser: the claude.ai website, the Claude desktop app, or a terminal program like Claude Code. In the Model Context Protocol's vocabulary, that app is called the MCP client.

The client sits between you and Claude. When you type a question, the client sends it to Claude and waits for a reply. When Claude decides to call a tool, the client does the actual network call to the MCP server, reads the result, and hands it back to Claude. When Claude is done, the client shows you the answer. Claude decides what to call; the client does the calling. From the MCP server's perspective, it doesn't matter which app you are using; the protocol is the same.

So: you ask the AI a question, Claude decides what to do, the client makes the tool calls, Claude reads the results, and eventually you see an answer. The server never sees your natural-language prompt; it only sees the structured tool calls. You usually don't see the individual tool calls either (unless the client chooses to show them); you see the answer.

Each MCP server offers a fixed, discoverable catalogue of tools. Every tool has a name, a description, argument types, and a machine-readable annotation of whether it is safe to call automatically (read-only) or needs the user's permission (destructive). The AI's client library reads this catalogue at connection time and uses it to decide what to call.

The key idea: the AI does not have magical access to anything you have not explicitly given it a tool for. An MCP server is a bounded surface. If a tool isn't in the catalogue, the action isn't available.

02 / This server

How this MCP works

Geodata MCP is an MCP server that exposes Stockholm's open municipal geodata to an AI chat. The catalogue includes SCB DeSO demographics, the SBK Stadskarta, and OSM addresses, pre-projected to EPSG:3011 and pre-joined to canonical keys. The server offers roughly forty tools: load a dataset, filter, intersect, classify, export, render a map image, and so on.

A typical session looks like this:

  1. You open Claude (in the browser or the desktop app) and connect to this server once, entering an invite code. That setup step is one-off.
  2. You ask a question in plain Swedish or English. Something like: Vilka fem DeSO:n i Stockholm har högst medianinkomst, och hur ser bebyggelsen runt omkring ut?
  3. Claude decides which tools to call. It might load the SCB income layer, join it with the SBK building layer, run a spatial buffer, classify the result, and call show() to mark the layers visible in a viewer.
  4. You get back an answer and a private viewer URL that shows the map. The viewer auto-refreshes as Claude does more work.
  5. If you want a shareable image of the map, Claude calls render_map() and hands you a PNG URL valid for twenty-four hours. You embed it in whatever document you are writing.

Everything runs in a session, a private workspace keyed to your connection. Your session has its own database, its own layers, its own visible styles. Nobody else can see it. If you close Claude and come back tomorrow, the session is still there; analyses resume where they left off.

Why it is stateful, and why that matters

Most web APIs are stateless: each request stands alone, the server forgets it the moment it is done, and the client has to include everything the server needs to do its job. That works well for simple request-response shapes. It works badly for the kind of iterative, composable work an LLM does when it analyses data.

This MCP server is stateful within a session. When Claude calls load("scb_income"), the resulting layer stays in your session. The next call, filter(...), operates on that loaded layer by name, not on a re-fetched copy. The call after that, annotate(...), writes columns into the same table. Twenty operations can compose over a shared workspace without re-downloading, re-projecting, or re-joining anything. The viewer looks at the same state.

This is one of the problems the Model Context Protocol is explicitly trying to solve. Earlier "function-calling" patterns for LLMs were stateless: every tool call was a self-contained RPC, and the LLM had to re-assemble context each time. That burns tokens (the LLM re-reads the same data repeatedly), burns time (network round-trips add up), and makes certain workflows effectively impossible (a five-step analysis would blow past context limits). MCP's session model gives the server a place to keep durable state that the LLM can reference by name, instead of by content.

Concretely, this session stores: the DuckDB database, the set of layers you have loaded, their column schemas and provenance, styles you have applied in the viewer, your operation history, any checkpoints you have created, and pagination cursors for in-progress iteration. All of that is persistent on disk on this server, so it survives reconnects and even service restarts. A session abandoned for two weeks gets cleaned up; a session you come back to tomorrow is exactly where you left it.

Everything the AI sees is authoritative

The tools the AI calls are authoritative. Spatial joins use real DuckDB spatial SQL over the actual source data, with the correct coordinate reference system. There is no "AI pretending to know geography." Every number in the answer was computed by a deterministic query against a named dataset, and every dataset carries its licence and citation all the way through the analysis.

03 / Pitfalls

Common misunderstandings

These are the things people trip on repeatedly. Most of them are corrections to intuitions imported from other tools (ArcGIS, QGIS, Excel, general-purpose chatbots, web search).

Pitfall 01

It is not a search engine

The AI does not have random-access memory of all 66 datasets. Every tool call retrieves exactly what it asks for. If you ask a vague question, Claude will narrow it down by calling search_data or describe_dataset first to find the right table. It is not searching a pre-built index of everything.

This means a question like "what does the data say about Södermalm" will not get a one-shot answer. Claude will iteratively pull relevant layers and join them. That takes a handful of seconds but is more accurate than a keyword search would be.

Pitfall 02

Memory lives on the server, not in the model

Claude has no persistent memory of your previous conversations. Each new chat starts fresh on the model side. What continuity you get across days comes from the session state stored on this server (layers, styles, operation log), which Claude rereads when you reconnect. The AI itself does not carry anything forward.

Separately, on training: under Anthropic's standard consumer terms, chat conversations may be used to improve future models unless you are on a plan that opts out (most enterprise and API plans do). Whether that matters for your work depends on what you discuss. The data this MCP exposes is public municipal data, so nothing confidential leaves your organisation through the chat, but if you paste internal documents into the prompt, that is a different question. Check the specifics of your Claude plan if you are not sure.

Nothing the MCP server stores (session state, exported files) leaves this server or feeds back into Claude's training.

Pitfall 03

LLM-authored columns are not the same as loaded data

You can ask Claude to classify every feature in a layer: tag each stadsdel with a dominant architectural era, for example. That works, and the values are written into a column as if they came from the source. But they did not. Claude invented them based on its training data plus whatever context you supplied.

The server tracks this. Every in-session column carries provenance: LLM-authored via annotate by model claude-opus-4-7 on 2026-04-19, or derived via add_field with this SQL expression. The viewer and sources() tool surface the distinction.

Check before you trust. If a column's values came from the LLM, treat them as candidate classifications to verify, not authoritative data. Spot-check a few and iterate.
Pitfall 04

It is not a replacement for ArcGIS or QGIS

This MCP is optimised for ad-hoc conversational queries that end in a rendered answer or a downloadable file. It is not for production cartography, not for complex map composition, not for manual feature editing, and not for raster or terrain analysis (no DEM loaded today).

For those workflows, export the relevant layer as a GeoPackage and open it in ArcGIS or QGIS. The MCP is where you decide what to export; ArcGIS and QGIS are where you polish it for print.

Pitfall 05

Claude can still hallucinate around the data

The numbers Claude reads from tool calls are authoritative. The prose Claude writes around those numbers is subject to the usual AI failure modes: misreading a column, confusing similar place names, inventing a plausible-sounding explanation for a pattern. The data is trustworthy; the storytelling on top of it needs the same scepticism you would apply to any AI-generated prose.

Rule of thumb: if Claude makes a claim, check it against the underlying layer. inspect and stats give you the raw rows and aggregates. If the prose and the rows disagree, trust the rows.

Pitfall 06

Sessions are private by default, not secret

Your session and its viewer URL are private to you until you share them. There is no shared workspace across users. If you want someone else to see your map, you send them the viewer URL. They can look, but they cannot tool-call against it; their own questions start a fresh session.

Conversely, the viewer URL has no password. Anyone you send it to can see the map. Only send it to people who should see the analysis.

Pitfall 07

Ad-hoc exploration, not a pipeline

This is the right tool for let me look at this quickly and what would that tell me. It is the wrong tool for a nightly-refreshed production job. The session model, the LLM-in-the-loop, and the 24-hour export TTL all assume exploratory work.

If an analysis becomes a recurring need, port it out: the SQL Claude writes is standard DuckDB, and the datasets are all publicly downloadable. A production pipeline is a different problem.

Pitfall 08

The AI is a collaborator, not a spec

Claude responds to ambiguity by making judgement calls. If your question is underspecified, Claude will pick a reasonable interpretation and proceed. That interpretation might not be yours.

The cure is to read what Claude did. The tool call log is usually visible in the client. Ask follow-ups. Ask Claude to show the SQL it ran. Treat it as a capable helper with good instincts, not a mind-reader.

04 / Try it

How to start

Access is invite-only. If you do not have a code, ask; the list of people with codes is currently small. With a code, the set-up is the same as any other custom claude.ai connector: a one-time paste of the endpoint URL, a confirmation screen, and the invite code.

The full connect flow and tool catalogue are on the landing page and in the docs. The docs cover design rationale, architecture, the data model, and the current roadmap.

Ask a question that matters for your work. The best way to see what this is good for is to use it on something concrete.
